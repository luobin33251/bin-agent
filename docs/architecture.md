# 架构设计

## 1. 设计目标与约束

来自需求讨论的四条硬约束，决定了后面所有的技术选择：

| 约束 | 来源 | 影响 |
|------|------|------|
| **不预设信息类型** | 「不要局限于信息的类型，要让 AI 自己归类」 | 数据模型只能是通用的「条目 + 类型」，不能有业务专有表 |
| **AI 自主归类** | 「我的对话过去了，AI 帮我分析归类」 | 需要一条「先检索已有类型 → 命中复用 / 未命中新建」的写入链路 |
| **本地优先** | 「只跑在自己电脑，手机通过内网访问」 | 用 SQLite 而非 MySQL；不引入需要独立进程的组件 |
| **文件不迁移** | 「不迁移，参考现有 D:\work 目录」 | 数据层只存文件路径与摘要，原始文件留在原地 |

## 3. Agent 运行机制

### 3.1 ReAct 循环

`Agent.run()` 是一个异步生成器，把「模型推理 → 工具执行 → 结果回灌」的过程
以事件流的形式逐步吐出，而不是等全部完成再返回。

```
用户消息
   │
   ▼
┌──────────────────────────────────────────┐
│ 1. 调 provider.chatStream(llmMessages)    │
│    逐块 yield assistant_message           │
└──────────────┬───────────────────────────┘
               │
               ▼
        有 tool_calls？
          │        │
         否        是
          │        │
          │        ▼
          │  ┌──────────────────────────────┐
          │  │ 2. 去重（name+arguments 相同只跑一次）│
          │  │ 3. 并行执行工具                │
          │  │ 4. yield tool_call / tool_result │
          │  │ 5. 结果回灌 llmMessages        │
          │  └──────────────┬───────────────┘
          │                 │
          │      ┌──────────┘
          ▼      ▼
       break ← 继续循环（最多 maxIterations 轮）
          │
          ▼
      yield done
```

关键实现在 [packages/bin-core/src/agent.ts](../packages/bin-core/src/agent.ts)。

### 3.2 工具结果回灌的协议要求

这是最容易踩坑的地方。回灌时必须满足 OpenAI 协议的两条约束：

1. **assistant 消息要带上本轮发起的 `tool_calls`**
2. **`role: "tool"` 的消息要用 `tool_call_id` 字段**（不是 `toolCallId`）

两者必须成对出现，否则第二轮请求会被接口拒绝（`tool message without a preceding tool_calls`）。
`OpenAICompatibleProvider.toApiMessages()` 负责这个转换。

> 注：参考项目在这一点上是不完整的（assistant 轮没带 tool_calls，
> tool 消息用的是 `toolCallId`），只是它对接的接口比较宽容才没暴露。本项目按规范实现。

### 3.3 工具结果的长度控制

超过 `MAX_TOOL_RESULT_CHARS`（60000 字符）的结果，只把开头部分喂给模型，
尾部追加一行截断说明。全量数据仍通过 `tool_result` 事件直达前端渲染。

这么设计的原因：模型通常只需要结果开头的概要字段，把全量明细塞进上下文
既浪费 token，也可能直接导致请求失败。

## 4. 工具系统

工具只需实现 `Tool` 接口（[packages/bin-core/src/tool.ts](../packages/bin-core/src/tool.ts)）：

```typescript
interface Tool {
  name: string;
  description: string;              // 模型据此判断何时调用，要写得具体
  parameters: ToolParameterSchema;  // JSON Schema 子集
  execute(params: Record<string, unknown>): Promise<string>;  // 返回字符串，通常是 JSON
}
```

`Agent.registerTool()` 注册后，`getToolDefinitions()` 会把
`name / description / parameters` 转成 OpenAI 的 tools 格式。

当前已注册工具见 [§5 写入闭环](#5-写入闭环m1-已实现) 的工具清单。

> M0 阶段先实现了一个 `list_item_types` 用于打通链路，M1 接入 `search_memory` 后已删除——
> 它的能力被 `search_memory`（空查询返回全部类别）完全覆盖，留着只会让模型在两件事上做选择。

## 5. 写入闭环（M1 已实现）

```
用户说一段话
   │
   ▼
① Agent 调 search_memory  ← 先检索：已有类别？已有条目？
   │
   ▼
② 把「建类别」与「写条目」合进同一个 save_memory：
   命中同名类别 → 复用（usage_count + 1）
   未命中       → 新建类别，status = 'active'，usage_count 从 1 起
   │
   ▼
③ 落库：entries（原话，不可变）→ items → links → search_index
   │
   ▼
④ 工具把卡片挂在结果的 _meta.card 上，路由层识别后补发 memory_card 事件
   前端渲染成结构化卡片 → 用户点「纠正」→ correct_memory 原地更新 + 追加留痕
```

三个设计要点：

- **"先查后写"是服务端逻辑，不是靠模型自觉**。把建类别和写条目合进 `save_memory`，
  模型就没法跳过复用判断。
- **卡片走「工具结果带元数据」而非新增 AgentEvent**。卡片是工具自己的产出，
  Agent 循环不需要知道它的存在——`_meta.card` 由路由层解析转发。
- **纠正采用「原地更新 + 追加留痕」**。条目原地改（否则列表里会出现两条一样的记录），
  但每次纠正都往 `entries` 追加一条写明「改了什么、从什么改成什么」，
  可追溯性由只增不改的 `entries` 保证。

写入前**先 search_memory** 是让 AI 越用越准的关键，不能省。
每次写入都要在 `entries` 表留下原话，AI 归类错了可以重新归类。

### 工具清单

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `search_memory` | 查类别与条目 | 空查询返回全部类别；FTS5 + LIKE 双路；**返回中区分「库里总量」与「本次命中」** |
| `save_memory` | 写入 | 内部处理新建/复用；原话必填；**落库前服务端查重** |
| `correct_memory` | 纠正 | 只传变化字段；无变化时拒绝写入 |
| `merge_memory` | 合并重复记录 | 保留 target，source 只补空缺后被软删除；**必须用户确认保留哪条** |
| `delete_memory` | 删除 | **软删除**；只有用户明确要求时才可调用 |
| `restore_memory` | 恢复已删除 | 软删除让这个动作总能成功 |

> `search_memory` 区分「库里总量」与「本次命中」是踩过坑的：早期版本在 `scope=types` 时
> 返回 `totalItems: 0`，模型据此向用户宣称「系统里什么都没记」——而数据好好在库里。
> 未查询的范围现在返回 `null`，不是 `0`。

**删除为什么是软删除**：删除不可逆，而这是一套「记忆」系统，误删的代价远高于留一行带标记的数据。
`items.deleted_at` 非空即视为已删除，所有查询与索引都排除它。这个过滤集中在仓储层，
不允许调用方自己拼 SQL 绕过。代价是每处查询都要记得带条件——所以过滤写在
`listItems` / `getItemById` / `searchItems` / `countItems` 内部，而不是交给调用方。

## 6. 类型自演化机制

「让 AI 自己归类」最大的风险是**类型碎片化**：今天建「服务器账号」，
明天建「服务器凭证」，最后什么都查不出来。三道闸控制它：

1. **复用优先**——写入前强制先检索已有类型，相似度达标必须复用
   （`createType` 在同名时返回 `null`，把「复用还是新建」的决定权留在 Agent 侧，
   而不是在数据层悄悄吞掉）
2. **孤儿标记**——`usage_count` 只有 1 的类型会在管理页单独列出，一眼看出碎片
3. **合并动作**——`mergeType(db, fromId, toId)` 把源类型标记为 `merged` 并把
   名下条目改挂到目标类型，历史数据一条不丢

`type_defs` 上的部分唯一索引保证了同名类型只存在一个：

```sql
CREATE UNIQUE INDEX idx_type_defs_name ON type_defs(name) WHERE status <> 'merged';
```

## 7. 检索层设计

检索走**两路混合**，用 RRF 融合：

| 路径 | 实现 | 适合 |
|------|------|------|
| 全文 | SQLite FTS5，`trigram` 分词器 | 精确词、专有名词、编号 |
| 语义 | 向量 + 余弦相似度 | 模糊描述、「上次说的那个空调的事」 |

两路的**输入文本是同一份**（`composeIndexText`：类别名 + 标题 + 摘要 + 状态 + 字段值）。
这一点是刻意的：如果关键词索引和向量各自拼各自的文本，就会出现
「关键词能找到、语义找不到」这种没法解释的行为。

### 几个关键取舍

**中文分词必须用 `trigram`。** SQLite 默认的 `unicode61` 分词器会把
**一整句中文当成一个词**，中文子串检索基本失效。`trigram` 按三字滑窗切分，
中文匹配效果好。这个在建表时就定了，改起来要重建索引。

**不引入 `sqlite-vec`，向量暴力检索。** 个人知识库规模在几千到几万条，
1024 维向量全量算余弦在 Node 里是毫秒级；而 `sqlite-vec` 是按平台编译的
原生扩展，在 Windows 上是额外的部署负担。向量以 BLOB 存在 `vec_index` 表里，
检索接口抽在 `search/vector.ts`，将来量大了再换实现，业务代码不用动。

**融合用 RRF，不把两路分数加权平均。** bm25 是负数、余弦是 -1~1，量纲不同，
加权前得先归一化，而归一化系数只能靠试、换个查询就失效。RRF 只看名次不看分数，
天然免调参（`k=60`，原论文经验值）。所以 FTS 那一路必须 `ORDER BY rank`——
名次错了，融合结果就跟着错。

**语义那一路有相似度下限（实测定为 0.4）。** 向量检索永远能返回「最像的几条」，
哪怕全是无关内容；没有下限，一次无关提问也必然挤进融合结果的头部，
把关键词命中的正确条目挤下去。

这个阈值是**量出来的，不是拍的**。用 `qwen3.7-text-embedding` 在真实数据上测：
真正相关的（换个说法的模糊提问）落在 **0.68~0.83**，同一语境但无关的落在
**0.30~0.41**。最初设 0.2 等于没设——问「上次那个空调的事」时库里根本没有空调记录，
却照样返回三条 0.23~0.33 的记录。

**过线的还会把分数交给模型。** 0.42 和 0.82 都「过线」，但含义差得远，
单靠阈值区分不了。所以每条命中的 `similarity` 和这一批的 `topSimilarity`
都写进工具结果，提示词明确要求：**最高分只有 0.4 出头时，就是没有真正相关的
记录，要如实说没找到，不许拿最像的那条硬凑**。

> 实测这一条起作用了：问「上次说的那个空调的事」时返回的唯一结果相似度 0.43，
> 模型没有硬答，而是说「没找到关于空调的内容，最接近的是 PDA 采购那条（相似度 0.43），
> 跟空调没直接关系」。只靠阈值过滤会把它当成「找到了一条」。

### 向量的写入与自愈

向量要调嵌入接口（异步 HTTP），塞不进 SQLite 事务，所以写入链路的规矩是：

```
落库（同步，事务）→ 算向量（异步，失败不影响落库）→ 启动自检补齐缺的
```

- 写入工具（save / correct / merge / restore）在落库后调一次 `vectors.indexItem()`
- 失败只记一条 warning——数据已经在库里了，只是暂时只能靠关键词找到它
- 服务启动时比对 `items` 与 `vec_index` 的差集，自动补算（后台跑，不挡启动）
- `pnpm reindex` 手动全量回填，用于换嵌入模型或排查索引问题

软删除时两个索引**一起摘**（`deleteItem` / `mergeItems`），恢复时重建 FTS、
向量留给上面那条自愈链——两个索引语义一致，才不会出现「删了还能语义搜到」。
换嵌入模型后旧向量因 `vec_index.model` 不匹配而自然失效，自检会把它们当成
「缺向量」重新算，不需要额外的迁移脚本。

> ⚠️ 嵌入模型配置**不回落**到对话模型配置。两者厂商、端点、计费都不同，
> 早期版本做了回落，结果是只能跑对话的套餐 key 被送去打嵌入接口，每次写入都 404。
> 现在 `EMBED_API_KEY` 留空即为「语义检索关闭」，启动日志会明确说出来。

**类别不做向量**，仍只按名称匹配。类别数量少、命名也由模型统一生成，
语义那路帮助有限，不值得再维护一套向量。

## 8. 技术选型

| 层 | 选择 | 理由 |
|----|------|------|
| 数据库 | SQLite (better-sqlite3) | 单人、本地、零部署；单文件即备份；内置 FTS5 |
| Web 框架 | Fastify 5 | 与参考项目一致；SSE 场景下直接操作 `reply.raw` 足够灵活 |
| LLM 抽象 | 自研 Provider 基类 | 各家都提供 OpenAI 兼容接口，统一实现即可 |
| 前端 | React 18 + Vite | 与参考项目一致，且后续 PWA 化成本低 |
| 样式 | Tailwind v4 + 自定义设计令牌 | 界面组件取自 [beautifului.dev](https://www.beautifului.dev/)，该站是 Tailwind 实现，详见 [design-system.md](design-system.md) |

数据库通过 WAL 模式（读写并发）+ `foreign_keys = ON`（保证级联删除生效）配置。

## 9. 与参考项目的关系

本项目参考了一个已有的内部 Agent 项目的架构，但不是 fork，是按需重写。

**直接沿用的设计**

- 三层结构：LLM 抽象 / Agent 核心 / 工具层
- ReAct 循环的事件流形态（`AgentEvent` 联合类型）
- 工具去重、结果截断、流式中断检测这些健壮性处理
- Fastify + React/Vite 的技术栈

**必须换掉或重写的部分**

| 项 | 参考项目 | bin-agent | 原因 |
|----|-----------|-----------|------|
| 数据库 | MySQL（只读连接业务库） | SQLite（读写） | 场景完全不同：前者面对线上业务数据，后者是本地单用户 |
| Provider | 每家厂商一个类 | 一个 `OpenAICompatibleProvider` + 配置 | 三家接口差异只在 baseUrl 和 model，没必要抄三份 |
| 工具组织 | 规划在独立包里（实际不存在） | `bin-server/src/tools/` | 按真实结构来，不照搬规划文档 |
| 动态 schema | 无 | `type_defs` 自演化 | 本项目的核心能力，参考项目没有 |
| 向量检索 | 无 | FTS5 + 向量混合 | 参考项目完全没有检索能力 |
| 移动端 | 无 | 响应式 + PWA（M5） | — |
| 密钥校验时机 | 构造 Provider 时抛错 | 调用模型时抛错 | 本地工具不该因为没填 Key 就拒绝启动 |

## 10. 安全设计（M4）

- **保险箱独立加密**：主密码经 scrypt 派生密钥，每条凭证用 AES-256-GCM 单独加密
- **明文不落盘**：数据层（`bin-db`）压根没有明文参数可写——它只接受 `Buffer` 密文，
  解密全部发生在 `bin-server/src/vault/` 里，密钥只存在于解锁后的进程内存中
- **自动锁定**：30 分钟无操作即清空内存中的密钥，之后任何读取都返回 401
- **不参与索引**：`vault` 表永不写入 `search_index` / `vec_index`
- **模型完全读不到**：不给 Agent 任何保险箱工具。因此「不进日志」是结构性保证——
  不是靠提示词约束模型别说，而是它根本没有拿到明文的通道

### 与原设计的偏差

| 原设计 | 实际做法 | 原因 |
|---|---|---|
| 主密码经 **Argon2id** 派生 | 用 `node:crypto` 的 **scrypt** | Argon2id 要引原生依赖，而 better-sqlite3 的编译坑刚踩过；scrypt 零依赖，强度够 |
| 前端解密后单独展开 | **服务端解密**，明文经响应返回 | 前端解密要用 WebCrypto，它只在安全上下文（HTTPS / localhost）存在。手机通过局域网 IP 访问时是 HTTP，`crypto.subtle` 根本不存在——那套方案会让最需要它的场景失效 |
| 每条凭证的账号、密码各存一列密文 | `cipher` 存**一条** JSON 密文（账号+密码） | GCM 的 iv 绝不能复用。两个字段各加密一次就得各配一套 iv，而表里只有一套 `iv` / `auth_tag` 列 |
| 对话里说密码怎么处理 | 照常记录 + 提醒风险（用户决定） | 代价写在明面上：会进 `entries`、发给云端模型、进检索索引 |

> 这一层与 `items` / `assets` 完全隔离，是独立的表与独立的访问路径。

## 11. 访问形态（M5）

服务端**同时托管前端构建产物**（`@fastify/static` + SPA 兜底），所以只有一个入口：

```
手机 / 电脑  ──HTTP──▶  http://<内网IP>:3100  ┬─ 静态资源（apps/web/dist）
                                              ├─ /api/chat/*    对话
                                              └─ /api/vault/*   保险箱
```

为什么必须合并成一个端口：手机要记两个地址（5173 + 3100）既麻烦又绕不开跨域；
本地开发仍然走 Vite（5173，带 HMR），生产形态走后端托管。

**为什么没做 service worker**：它要求安全上下文（HTTPS 或 localhost）。
当前的形态是「局域网 HTTP 直连」，注册不了——硬做只会得到一个静默失败的 PWA。
所以 M5 只做「manifest + 图标 + 加到主屏幕 + 移动端适配」，等接上 Tailscale
（能拿到 `.ts.net` 的 HTTPS）再补离线能力。
